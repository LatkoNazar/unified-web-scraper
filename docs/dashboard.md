# Перегляд датасетів і живий збір

Запусти з кореня проєкту:

```powershell
uv sync --locked --dev --extra browser
uv run playwright install chromium
uv run python -m unified_web_parser serve --host 127.0.0.1 --port 8001
```

Відкрий [інтерфейс](http://127.0.0.1:8001/). Окремий Node-сервер, npm install
або frontend build не потрібні: FastAPI віддає HTML, CSS і JavaScript пакета.
CLI читає локальний `.env`; ключі залишаються на сервері.

Інтерфейс використовує теплий папір, стримані акценти й локальні шрифти.
На головному екрані — запит, результати й історія. Додаткові параметри, журнал,
фільтри та колонки розгортаються за потреби. Верхня панель із вартістю й кнопкою
зупинки залишається доступною під час прокручування.
Походження збереженої графіки та ліцензії шрифтів: [UI assets](ui-assets.md).

## Запуск із питання

1. Напиши, що знайти та які поля зібрати.
2. Типово схема й вибір полів автоматичні; додаткові параметри необов'язкові.
3. За потреби відкрий «Налаштування збору»: там є профіль «Автоматично» або
   YAML-профіль, конкретні HTTP(S) URL, HTTP/браузер і ліміти сторінок, записів та API-спроб.
4. Натисни «Почати збір». Без списку сайтів працює web discovery, зі списком —
   пошук і обхід заданих джерел.

Профілі задають доменні правила, але інтерфейс універсальний: картки, таблиця й деталі
показують довільні поля `Record.data`. «Без AI» використовує фіксовану схему та
детерміновані правила. Web search лишається платним і вимагає ключа та ненульового
бюджету; для збору без нього вкажи джерела й вимкни AI.

## Типи, колонки та автоматичні фільтри

У режимі «Автоматично» AI спочатку створює попередню схему з питання для пошуку
та навігації. Потім pipeline оглядає зразок уже завантажених сторінок, обраних
для extraction: JSON-LD, текст описів і DOM-блоки. Одна додаткова обмежена спроба
уточнює типи, характеристики та рекомендовані колонки перед першим витягуванням
записів. Фінальна схема однакова для всього запуску. Це не AI-запит на кожну картку;
уточнення використовує той самий бюджет API та кеш і не завантажує сторінки повторно.
Фіксована схема профілю й схема replay залишаються авторитетними та не уточнюються.

Поля мають JSON-тип, підпис, необов'язкові одиницю та формат. `presentation` у
snapshot описує колонки й статистику за фактично зібраними записами:

Одиниця — підпис числового поля, а не механізм конвертації: значення з джерел
не переводяться автоматично між валютами або різними одиницями виміру.
Для локальної перевірки `date-time` явно встановлено `rfc3339-validator`:
[`jsonschema` потребує додаткового пакета для цього формату](https://python-jsonschema.readthedocs.io/en/stable/validate/#validating-formats).

| Поле | Тип | Автоматичний фільтр |
| --- | --- | --- |
| Цикли, діагональ, зарплата | integer / number | «Від — До» з межами вибірки |
| MDM як явне так/ні | boolean | фактичні значення «Так» / «Ні» |
| Статус MDM, місто, категорія | string | унікальні значення з кількістю записів, до 40 варіантів |
| Дата | string + date/date-time | діапазон дат |
| Текст із багатьма унікальними значеннями | string | пошук підрядка |
| Списки | array | пошук у тексті JSON списку |
| Вкладена структура | object | перегляд у деталях |

Кожен доступний фільтр також дозволяє обрати лише заповнені або лише невідомі
значення. `null` та відсутнє поле — невідомі; `0` і `false` — справжні значення.
Межі та кількості рахуються за всією вибіркою цього запуску, до застосування UI-фільтрів.
Це локальні фільтри датасету: вони не змінюють фільтри на сайтах і нічого не відсіюють
під час crawling. Кілька умов поєднуються через AND.

Кнопки «Картки» / «Таблиця» використовують спільний план колонок.
У «Колонки та характеристики» можна змінити його вручну або відновити автоматичний.
Деталі завжди містять усі вихідні поля. Нові записи оновлюють діапазони й категорії
наживо, зберігаючи введені фільтри. Інший запуск починає з чистими фільтрами.
Старі збережені датасети теж отримують типи й фільтри зі своєї схеми та значень,
без нового платного AI-запиту; для них немає нового змістового планування за описами.

AI бачить обмежений зразок, тому рідкісна характеристика лише на пізніших сторінках
може не потрапити в автоматичну схему. Для обов'язкових полів вкажи їх у запиті
або власній схемі. Повноту всіх можливих характеристик система не гарантує.
Модель також може обрати невдалий тип або пріоритет колонки: UI використовує
заявлений тип, не вгадує числа з довільного тексту. Колонки можна змінити в UI;
для гарантованого типу потрібна явна JSON Schema.

## Що оновлюється наживо

```text
Браузер → POST /runs → 202 + run_id
                     ↓
              фоновий PipelineRunner
                     ↓
     реальні етапи / лічильники / валідовані записи
                     ↓
          GET /runs/{run_id}/events (SSE)
                     ↓
        картки, зображення, прогрес, журнал
```

Перші записи з’являються після extraction і валідації, ще до завершення обходу.
UI позначає їх як **попередній перегляд**. SQLite/PostgreSQL та файлові експорти
записуються наприкінці pipeline; `records_persisted` і `persisted` показують
фактичний стан запису в локальний датасет, а не припущення інтерфейсу.

Лічильники відображають отримані сторінки, спроби завантаження, знайдені записи
та відомий AI usage. Смуга «N / ліміт» показує використаний бюджет обходу,
а не відсоток повноти інтернету чи сайту. Журнал містить останні події;
повний аудит залишається в artifacts.

## Вартість і зупинка

Вартість у верхній панелі оновлюється після кожної відповіді моделі або вебпошуку,
навіть якщо її результат не пройшов валідацію. Значення береться з provider usage,
а не розраховується за приблизною ціною токенів. Після завершення сума залишається
в запуску й відновлюється з історії.

- `ai.known_cost_usd` — сума вже отриманих cost metadata.
- `ai.cost_complete` — чи відома вартість усіх фактичних спроб.
- `ai.cost_pending_calls` — кількість спроб, для яких немає cost metadata.
- `ai.in_flight_calls` — запити, що ще виконуються.
- `ai.cost_usd` — повна сума, тільки коли дані повні.

Якщо metadata неповні, відома сума залишається видимою з позначкою неповноти.
Невідома вартість не стає `$0`. Сума не збільшується за таймером: вартість поточного
незавершеного запиту стане відомою лише після відповіді провайдера. Для перерваного
мережевого запиту остаточне списання може лишитися невідомим у цьому звіті.

Кнопка зупинки припиняє збір і зберігає вже сформовані валідні записи;
недооброблені сторінки не запускають новий extraction. Термінальний статус ручної
зупинки — `cancelled`, причина — `user_cancelled`.

При відповіді OpenRouter про недоступні кредити весь запуск переходить у `stopped`
з `stop_reason: credits_exhausted`. Нові AI-запити не надсилаються, готові записи
зберігаються, причина показується окремим повідомленням. Це не низка помилок
extraction для кожної наступної сторінки. Відповідь про тимчасовий in-flight spending
cap пояснюється як обмеження одночасних витрат, а не як нульовий баланс.
Помилки ключа, rate limit та інші збої не видаються за відсутність грошей.

Контракти провайдера: [usage accounting](https://github.com/OpenRouterTeam/docs/blob/main/cookbook/administration/usage-accounting.mdx)
і [credit limits](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/limits.mdx).

SSE автоматично перепідключається. При проблемі з потоком UI додатково отримує
snapshot раз на три секунди; старі ревізії не перезаписують нові результати.
Перезавантаження сторінки й відкриття `/?run=<run_id>` відновлюють перегляд.
Відключення вкладки не зупиняє збір. Термінальний стан після зупинки з'являється
після очищення ресурсів і збереження готових записів.

Поточна версія виконує один активний UI-запуск за раз; місткість можна явно
налаштувати через `create_app(max_active=2)`. Це локальні supervised asyncio tasks,
без зовнішньої черги або scheduler. У пам’яті зберігаються до 20 запусків і 200 log-подій
на запуск; snapshots журналюються у `data/live/`. Старі завершені запуски доступні
зі своїх artifacts, а не з поточного стану записів іншого запуску.

Після різкої зупинки процесу незавершений журнал позначається перерваним:
автоматичного поновлення crawling немає. Зокрема, автоматичне узгодження журналу
з artifacts у момент збою між їхнім збереженням не гарантується. Звичайна ручна
зупинка зберігає готові записи; аварійне завершення процесу або помилка диска
не мають такої гарантії. Фактичний стан видно за `persisted` і `records_persisted`.

## `img_url`

Зображення — необов’язкове поле **envelope запису**, окремо від довільної схеми `data`:

```json
{
  "record_id": "…",
  "job_name": "…",
  "img_url": "https://example.org/media/item.jpg",
  "data": {"title": "Назва запису", "url": "https://example.org/item"},
  "provenance": {"…": "…"}
}
```

Якщо підтвердженого зображення немає, значення `null` і UI показує заглушку.
Джерела: JSON-LD `image` / `thumbnailUrl` / `ImageObject`, пов’язане з записом
DOM-зображення (`src`, lazy loading, `srcset`), а для однозначної detail-сторінки —
`og:image`. Відносні адреси розв’язуються від URL сторінки. Вбудовані/активні URL
і розпізнані placeholder відкидаються. DOM-зображення з ознаками logo/favicon/icon/avatar
чи з допоміжних областей пропускаються. Прив’язка до сутності консервативна:
неоднозначним карткам не роздається спільна обкладинка сторінки. Це перевірка
спостережених посилань і структури, а не семантична перевірка вмісту фотографії.
LLM не генерує це metadata; окремих AI-запитів для картинок немає.

Закрита JSON Schema користувача не змінюється. Якщо вона явно має власне `img_url`,
mapper також може заповнити його за спостереженим джерелом. Автоматичний UI бере
картинку з envelope `img_url`. Зображення завантажує браузер напряму, з lazy loading,
без referrer; при недоступній картинці лишається заглушка.

Поточний стан та історія SQLite/PostgreSQL мають nullable `img_url`; старі таблиці
оновлюються ідемпотентно. `data_hash` і далі рахується лише з `Record.data`,
але зміна `img_url` також створює snapshot історії. Звичайна URL/identifier identity
не залежить від envelope `img_url`; попередня content-fingerprint identity
й далі залежить від вихідного evidence, яке може містити зображення.

JSONL/API мають поле `img_url`, CSV/Parquet — metadata-колонку `_img_url`.
Старі збережені записи отримують `null`; для витягування зображень із наявного HTML
можна виконати `reprocess --no-ai`, без нового crawling.

## Перевірка

```powershell
uv run pytest -q
uv run python tests/integration/check_dashboard.py
node --test tests/frontend/dataset.test.mjs tests/frontend/cost.test.mjs
```

Друга команда запускає справжні FastAPI, HTTP-джерело, pipeline, SSE та Chromium
на loopback без AI. Перевіряє появу запису до commit, зображення, перепідключення,
історію, фільтри, деталі, JSON download, захист від старих snapshots і мобільний вигляд.
Покриває типізовані фільтри, ручні колонки та збереження фокусу на кнопці запису
після progress-only SSE й додавання нового рядка. Довгі значення в таблиці
показуються як прев'ю до трьох рядків; повний текст залишається в деталях.
Окремі локальні snapshots перевіряють накопичення ціни, неповні metadata,
ручну й кредитну зупинку та закріплені кнопки на ширині 1440, 390 і 320 px.
Ці сценарії не виконують платних API-запитів.
Результат і screenshots: `data/dashboard-check/`.
