# Unified Web Parser: повний технічний опис для підготовки резюме

Цей документ можна передати агенту, який готуватиме резюме, portfolio case study
або опис проєкту для співбесіди. Він описує фактично реалізовану систему,
а не початкові плани з листування. Звірено з кодом версії пакета `0.2.0`,
конфігураціями, документацією та результатами перевірок у цій робочій сесії.
Дата опису: 24 жовтня 2026 року.

Числа нижче — результати конкретних локальних перевірок і збережених запусків.
Це не production SLA, не поточні тарифи сторонніх сервісів і не підтвердження
доступності всіх сайтів на майбутнє. Розділи про особистий внесок потрібно
узгодити з власником проєкту: перелік можливостей системи сам по собі не
встановлює, які роботи людина виконала особисто.

## 1. Суть проєкту

**Unified Web Parser — конфігурований Python-рушій для пошуку, автономного
обходу сайтів і перетворення вебконтенту на структуровані, перевірені та
простежувані датасети за заданою або згенерованою схемою.**

Користувач може передати питання природною мовою, конкретні URL, джерела
пошуку на сайтах або sitemap. Система знаходить джерела, розпізнає доступні
елементи навігації, обирає потрібні блоки сторінок, витягує факти, перевіряє
схему, зберігає записи та показує перебіг роботи у вебінтерфейсі.

Основний принцип: використовувати спостережувані структуровані дані й
детермінований код там, де цього достатньо, а AI — для неоднозначних рішень,
планування та складного витягування. Повний HTML кожної сторінки не потрібно
безумовно передавати великій моделі.

Перший практичний кейс — збір оголошень MacBook із OLX та магазинів. Проте
поля ноутбука не є моделлю ядра. Ядро працює з `Page`, `CandidateBlock`,
`Record`, планами навігації та JSON Schema. Предметні дані містяться у
`Record.data`; товарні та device-правила вмикаються явно.

Той самий механізм можна налаштовувати для статей, вакансій, книг, подій,
організацій та інших сутностей. Це розширюваність архітектури, а не обіцянка
безпомилкового збору будь-якого сайту без конфігурації.

## 2. Яку проблему вирішує система

Звичайний site-specific scraper часто містить зашитий URL пошуку, CSS-селектори
й структуру конкретного товару. Зміна сайту або предметної області вимагає
нової реалізації. Суцільний LLM-парсинг, своєю чергою, збільшує витрати,
неоднозначність та складність відтворення результату.

У цьому проєкті задача розділена на незалежні частини:

1. Які джерела шукати?
2. Які спостережувані дії на сайті можуть наблизити до потрібних даних?
3. Які блоки сторінки є потрібними сутностями?
4. Які факти вже є у JSON-LD або DOM?
5. Які поля справді потребують LLM-доповнення?
6. Чи відповідає результат схемі та правилам допуску?
7. Як зберегти результат, його походження, історію та фактичні витрати?
8. Як продовжити роботу після збою або дозібрати нові сторінки без зайвої оплати?

Цінність проєкту — поєднання AI з контрольованим data pipeline:
типізовані контракти, обмежені дії, локальна валідація, збережені докази,
облік вартості та відновлення стану.

## 3. Що подається на вхід і що виходить

### Входи

- Питання природною мовою: що знайти та які характеристики зібрати.
- Список абсолютних HTTP(S) URL сайтів, каталогів або детальних сторінок.
- Sitemap або sitemap index.
- YAML-конфігурація job із джерелами, профілями, моделями та лімітами.
- Власна JSON Schema або дозвіл згенерувати її з питання.
- Раніше збережені snapshots для повторної обробки без crawling.
- ID перерваного або завершеного запуску для `resume` чи `update`.

### Виходи

- Типізовані записи у спільному envelope: фактичні поля, `img_url`, provenance.
- Поточний локальний датасет SQLite та історія змін записів.
- Окрема вибірка й артефакти кожного запуску.
- JSONL, Parquet, CSV; необов'язкова додаткова копія у PostgreSQL.
- REST API для запуску, перегляду, історії, зупинки та продовження.
- Live UI із картками, таблицею, фільтрами, прогресом та витратами.
- Аудит пошуку, навігації, routing, admission, помилок і coverage.
- Checkpoint та журнал платних запитів для відновлення після збою.

Приклад питання:

> Знайди MacBook Air або Pro з M5, конфігураціями 16/512, 16/1TB чи 24/1TB.
> Цікавлять розпаковані або як нові. Збери назву, ціну, RAM, SSD, стан,
> цикли батареї, статус MDM, посилання та зображення.

Це задача збору та подальшого перегляду фактів. Питання не перетворює систему
на засіб перевірки продавця, справжності пристрою або гарантованої рекомендації купівлі.

## 4. Архітектура

Система побудована як **модульний моноліт із pipeline-oriented architecture**.
Одиниця роботи — job/run, а центральний координатор — `PipelineRunner`.
FastAPI є одним з інтерфейсів. CLI виконує той самий pipeline без вебсервера.

```text
CLI / FastAPI / Live UI
          ↓
     PipelineRunner
          ↓
Схема → Discovery → Crawl / Navigation → Candidates / Routing
                                              ↓
                              Extraction + Identity → Validation
                                              ↓
                              Merge → Validation → Admission
                                              ↓
                            Durable record commit / Live events
                                              ↓
                         Assessment / Final persistence / Exports
```

Компоненти створюються на межі запуску; fetcher, LLM-клієнти та store можна
передати в конструктор. Це спрощує заміну провайдерів і тести без платних
викликів. Водночас у поточному коді немає складного dynamic plugin registry
чи автоматичного завантаження плагінів через package entry points.

### Карта модулів

| Модуль | Відповідальність |
| --- | --- |
| `core` | Pydantic-моделі, строгі конфігурації, локальна JSON Schema, помилки |
| `schema_generation` | Обмежений AI-план полів і локальна компіляція схеми |
| `discovery` | План пошукових запитів, об'єднання джерел, sitemap |
| `navigation` | Inventory форм і дій, rules/AI-план руху, політика дій |
| `crawling` | Обробка сторінок, DOM helpers, rate limiting, access-page detection |
| `routing` | Побудова кандидатів та вибір блоків і стратегій extraction |
| `extraction` | JSON-LD/DOM mapping, LLM enrichment, identity, provenance, images |
| `processing` | Валідація, merge/deduplication, допуск записів |
| `profiles` | Явно ввімкнені предметні евристики |
| `assessment` | Оцінка вже витягнутих фактів за підтримуваними правилами |
| `providers` | HTTP, Crawl4AI, browser actions, OpenRouter, usage journal |
| `pipeline` | Lifecycle, черга обходу, schema session, checkpoint, persistence |
| `storage` | SQLite/PostgreSQL, історія, експорти, leases, incremental ledger |
| `interfaces` | CLI, API, live manager, presentation metadata, frontend |

Код: `src/unified_web_parser/`. Докладна карта: [architecture.md](architecture.md).

## 5. Повний шлях одного запуску

### 5.1. Прийняття та перевірка задачі

CLI читає аргументи й локальні налаштування, завантажує YAML, застосовує явні
overrides. API валідує тіло запиту та створює `LoadedJob`. Невідомі параметри
конфігурації, дублікати YAML-ключів і невалідні джерела відхиляються.

Якщо передана ручна схема, вона перевіряється до обходу. Посилання схеми
обмежені локальними внутрішніми references: для валідації не потрібно
завантажувати довільні віддалені схеми.

Створюються `run_id`, каталог запуску, звіт, checkpoint та клієнти зі спільним
бюджетом. OS lease захищає запуск від одночасного виконання двома процесами.

### 5.2. Автоматична схема з питання

Якщо ввімкнено auto-schema, модель спочатку пропонує **план полів**, а не
виконуваний код і не довільну схему з віддаленими references. Код перевіряє
план і сам складає закриту JSON Schema.

План може визначити:

- Назву сутності та назви полів.
- Типи `string`, `number`, `integer`, `boolean`, масиви простих значень.
- Українські підписи, одиниці виміру, формати дат.
- Ролі полів і початковий порядок колонок у UI.

`title` та `url` є обов'язковими непорожніми значеннями. Інші згенеровані поля
також присутні у `required`, але допускають `null`, коли доказів немає.
Типовий ліміт — 20 полів, дозволено 2–30;
розмір згенерованої схеми обмежено 32 KiB. Довільні вкладені object-структури
автоматичний генератор поки не будує; їх можна задати власною схемою.

Далі система накопичує до трьох придатних сторінок. До моделі передаються
обмежені приклади JSON-LD, описів, атрибутів або карток, щоб **один раз
уточнити схему за реальними даними**. Після цього схема фіксується на весь run.
Сторінки з буфера не завантажуються повторно.

Так система може побачити важливі характеристики, яких бракувало в першому
плані. Проте зразок обмежений: рідкісне поле з пізнішої сторінки може не
потрапити у схему. Обов'язкові характеристики краще назвати у питанні або
закріпити власною схемою.

Початкова невдала генерація зупиняє запуск. Невдале контекстне уточнення
має явний аудит і може залишити вже валідну попередню схему.

### 5.3. Пошук джерел у вебі

Етап потрібен для `discover`. Якщо користувач уже передав джерела, повторний
web search не є обов'язковим.

Планувальник формує кілька варіантів web-запиту та короткий `site_search` для
пошуку всередині сайту. Оригінальне питання зберігається окремо від короткого
пошукового формулювання.

Типові налаштування discovery — до трьох запитів, до 25 результатів на запит
і максимум 25 унікальних сайтів. Це змінні ліміти, а не обіцянка отримати
рівно 75 URL або повністю обійти інтернет.

Пошук реалізований через **OpenRouter Web Search Server Tool**
`openrouter:web_search`. Використовуються обов'язковий tool-виклик, ліміти
використання та перевірка фактичного usage. На одну HTTP-спробу встановлено
ліміт одного виконання пошуку; retry є новою спробою і теж враховується.
Deprecated Web Search Plugin та неявний `:online` механізм не використовуються.

URL беруться зі структурованих citations/annotations відповіді, а не з
довільно написаних моделлю посилань у тексті. Є TTL-кеш пошукової видачі.

Результати кількох запитів об'єднуються. Дублікати сайтів визначаються за
зареєстрованим доменом із Public Suffix List; незалежні tenants на приватних
суфіксах не потрібно помилково об'єднувати. У режимі `site_root` рушій
починає від кореня знайденого сайту; у `result_url` — від повернутого URL.

Це дедуплікація джерел, а не глобальне розпізнавання однакових товарів у
різних магазинах.

### 5.4. Завантаження сторінки

Є два явно обрані backend:

- `http`: `httpx` отримує HTML без виконання JavaScript.
- `browser`: Crawl4AI використовує браузерний механізм на основі Playwright/
  Chromium, рендерить JS і підтримує взаємодії зі сторінкою.

Автоматичного універсального перемикання HTTP → browser при кожній помилці
немає. HTTP і браузерна версія одного сайту можуть показувати різний вміст.

Зберігається `Page`: URL, час отримання, HTTP status, HTML, `page_id` і
посилання на snapshot. HTML-знімок потрібен для аудиту, повторного extraction
та відновлення без нового відкриття джерела.

Сторінки блокування/captcha відрізняються від нормальних результатів і
реєструються як помилки доступу. Обхід captcha не реалізований.

### 5.5. Як знаходиться пошук без зашитого URL сайту

`InventoryBuilder` розбирає завантажений DOM і будує набір **спостережуваних
можливостей сторінки**:

- Пошукові input/form, метод форми, назви параметрів і кнопки submit.
- Schema.org `SearchAction` та спостережений URL template.
- Кнопки відкриття пошуку для JS-інтерфейсів.
- Категорії та посилання на сутності.
- Пагінацію, load-more, доступні select options і scroll.
- Ознаки сторінки результатів або окремої сутності.

Кожна дія отримує `action_id` та прив'язку до конкретного `page_id`. Селектори,
значення options і URL формує код зі спостереженого DOM. Модель не вигадує
для виконання довільний selector, новий шлях `/search` або JavaScript.

`NavigationPlanner` у режимі `rules`, `ai` або `hybrid` обирає існуючі action IDs,
потребу extraction або причину зупинки. План перевіряється: невідома дія,
повторний ID чи план для іншого snapshot не виконуються.

Для звичайної GET-форми код складає URL із реально знайденого action і
параметра input. Для JS-форми browser backend вводить запит і виконує
дозволену прив'язану дію. Після переходу або мутації DOM inventory будується
заново.

Типово навігаційні фільтри ціни, географії, характеристик і сортування
вимкнені. Це допомагає не звужувати пошук зайвими controls. Їх можна
дозволити явно. Фільтри вже зібраного датасету в UI — окремий механізм.

### 5.6. Обхід графа сторінок і станів

`CrawlEngine` веде чергу робіт, відвідані URL, виконані дії, поточні browser
стани та походження гілок. Це обмежений обхід графа спостережуваних переходів,
а не безконтрольне рекурсивне відкриття всіх посилань.

Пагінація не повинна витрачати глибину так само, як перехід у нову категорію.
Підтримуються результати з окремими detail URL, звичайні наступні сторінки,
load-more та lazy-loaded списки. Стан враховує не лише адресу, а й observation
сторінки/viewport, оскільки кілька JS-станів можуть мати той самий URL.

Параметри обмежують сторінки, глибину, записи, дії на URL, розмір inventory,
кандидатів, HTML, час запитів, retries та AI calls. Discovery має також
спільний per-site budget для URL одного сайту.

HTTP fetch може виконуватися пакетами з налаштованою concurrency. Після
отримання пакета навігація та обробка сторінок координуються послідовно;
це не паралельний кластер LLM-воркерів. Browser-взаємодії послідовні, щоб
не змішувати стани. Для host діє rate limiter.

Після використання browser page звільняється; сторінка з pending UI-дією
утримується до потрібної взаємодії. `navigation.jsonl` зберігає inventory,
план, виконані дії, результати, звільнення ресурсів і причини зупинки.

Coverage повідомляє про вичерпання **спостережуваного** frontier або неповноту
через ліміти/помилки. Статус успішного pipeline не доводить, що знайдено
кожне оголошення всього сайту.

### 5.7. Побудова кандидатів і рішення, що саме парсити

`CandidateBuilder` виділяє із HTML обмежені блоки:

- JSON-LD сутності, включно з елементами списків/графів.
- Семантичні DOM-картки, рядки таблиць і блок основної сутності.
- Текстовий fallback, коли структурованих доказів недостатньо.

Блок має `candidate_id`, kind, content і locator. Тобто AI отримує компактний
набір релевантних кандидатів із відомими ID, а не необов'язково весь HTML.

**Block Decision Engine працює до extraction.** Він обирає, які кандидати
обробити, та одну зі стратегій: `json_ld`, `dom`, `llm`, `skip`.

Режими:

- `rules`: детермінований вибір придатних структурованих/DOM-блоків.
- `ai`: вибір routing-моделлю.
- `hybrid`: дешевий fast path лише для достатньо однозначного випадку,
  і AI routing для решти.

У реалізованому fast path guard перевіряє, зокрема, єдиний JSON-LD кандидат,
непорожній description та явний URL/identity цієї сторінки без суперечностей.
Кілька сутностей, неоднозначні identities або брак потрібних доказів
повертають вибір до AI.

`RoutingPlan.validate_against` перевіряє snapshot і candidate IDs. План не
може послатися на неіснуючий блок. Confidence/probabilities, коли їх
повертає Decisions, потрапляють в аудит; це не калібрована ймовірність
правдивості оголошення.

### 5.8. Витягування: JSON-LD → DOM → LLM

Структуровані факти використовуються першими. JSON-LD може вже містити
назву, URL, автора, дату, image, offers та інші атрибути. DOM може додати
видимий заголовок, опис, атрибути й поля конкретної картки.

Проєкція використовує схему, точні назви, явні `x-source` mappings і
підтримувані semantic aliases. Товарні `offers` та money-евристики належать
до явно обраного `commerce` профілю. Поле `price` саме по собі не перемикає
універсальний job у режим товарів.

Це не обов'язково три окремі запити й не безумовна черга трьох повних парсерів.
Routing обирає стратегію; extractor використовує доступні докази та може
звернутися до LLM лише для необхідного доповнення.

LLM отримує в `evidence` саме вміст обраного кандидата (`candidate.content`).
Опис із сусіднього DOM-блоку не додається до JSON-LD автоматично. Щоб модель
витягнула факт, він має бути у переданому evidence; інакше правильним
результатом є невідоме значення, а не здогадка за всією сторінкою.

У sparse enrichment модель отримує evidence обраного кандидата та схему
лише потрібних доповнень: відсутніх/null або конфліктних полів. Уже
спроєктована структурована основа залишається локально; окремий base record
у payload не передається. Відомі значення не потрібно генерувати повторно.
Результат зливається локально;
source facts мають пріоритет, а суперечності зберігаються у підтримуваному
контракті замість тихого переписування.

Sparse projection вмикається лише для безпечного класу схем. References,
open objects, composition та cross-field constraints можуть вимагати
повної схеми, тому існує fallback на full-schema extraction.

За помилки AI routing є явний warning і fallback на правила. За помилки
LLM extraction зберігається error і може використовуватися детермінований
результат. Автоматичного непомітного перемикання на іншу платну модель немає.
Невідомі значення залишаються `null`, якщо це дозволено схемою, або відсутніми.

### 5.9. Валідація та admission

Pydantic перевіряє внутрішні повідомлення, конфігурації та плани. Окремий
`jsonschema` перевіряє довільні фактичні поля запису за ефективною JSON Schema.
Синтаксично правильний JSON не є достатньою умовою прийняття.

Після первинної schema validation записи з однаковою identity за потреби
зливаються й проходять повторну перевірку. Далі працює admission:
`accepted`, `review` або `rejected`.
Пояснення зберігаються в `admission.jsonl`, відхилені оригінали — окремо.
`review` може залишатися у звичайній вибірці; спеціальний historical repair
з `--confirmed-only` дозволяє винести неоднозначні записи окремо.

У профілі `device` перевіряється предмет оголошення: чохол **для MacBook**
не має стати ноутбуком через перелік сумісних моделей, а ноутбук **із чохлом
у комплекті** не повинен бути помилково відхилений. Явно інші моделі,
запчастини, аксесуари й послуги відокремлюються від цільових пристроїв.
Ці правила не нав'язуються `generic`-сценаріям.

Schema validation гарантує структуру, а не істинність інформації джерела.
Admission зменшує забруднення вибірки, але не є універсальним семантичним
класифікатором із доведеною точністю для всіх доменів.

### 5.10. Identity, дедуплікація та історія

Ідентичність формується за доказами джерела: URL сутності, source identifier/
SKU, URL сторінки або content fingerprint як fallback. Ураховується job
і джерело. Canonical URL прибирає відомий tracking і fragments, зберігаючи
значущі параметри ресурсу.

Це дозволяє стабільно оновлювати повторно побачений запис, об'єднувати його
спостереження та не множити дублікати в межах підтримуваної identity.
Fallback за контентом слабший: зміна evidence може створити нову identity.

Не реалізовано глобальне entity resolution, яке доводить, що два продавці
на різних сайтах продають один і той самий фізичний ноутбук. Не слід
заявляти про «ідеальну дедуплікацію всього інтернету».

Upsert зберігає current state, first/last seen та походження. Зміна даних
або зображення створює history snapshot; повтор незмінного запису не повинен
дублювати історію змін.

### 5.11. Зображення

Універсальне nullable `img_url` зберігається в envelope окремо від довільної
схеми `data`. Джерела: власне JSON-LD image/thumbnail/ImageObject, itemprop,
галерея, DOM-картка з точним посиланням, `src`, lazy-loading атрибути та `srcset`.
Open Graph використовується лише з перевіркою належності detail-сторінці.

Відносні адреси перетворюються на абсолютні. Розпізнані підтримуваними
евристиками логотипи, іконки, placeholders, активні/вбудовані URL та
неоднозначні чужі зображення відкидаються.
Загальна обкладинка каталогу не повинна стати фото кожного товару.

AI не генерує адреси фото. Окремих LLM-запитів для цього механізму немає.
Розпізнавання предмета на самій фотографії, OCR та computer vision не
реалізовані. Фото може пізніше стати недоступним; UI має fallback-заглушку.

### 5.12. Assessment після extraction

Після витягування існує окремий шар інтерпретації підтримуваними правилами.
У device-профілі це, наприклад, `is_relevant`, `has_mdm_risk` і
`requires_manual_review`.

Він відрізняється від AI Decisions для navigation/routing. Поточний
післязбірний assessment не слід описувати як навчений AI-скоринг вигідності.
Невідомий MDM — не підтверджена відсутність MDM. Заява продавця про батарею,
гарантію чи керування пристроєм залишається заявою джерела.

Калібровані оцінки шахрайства, автоматичне BUY/REJECT, ринкова медіана та
повноцінний deal scoring не є реалізованою функціональністю поточного ядра.

## 6. Невеликий приклад перетворення даних

Приклад нижче **навчальний**, не реальне оголошення і не реальна ціна.
Він показує типи даних на межах етапів; це не дослівні provider payloads.

### HTML сторінки

```html
<h1>MacBook Air M5 24GB / 1TB, Open Box</h1>
<script type="application/ld+json">
{
  "@type": "Product",
  "name": "MacBook Air M5 24GB / 1TB, Open Box",
  "url": "https://shop.example/item/42",
  "description": "Розпакований. M5, 24 GB RAM, SSD 1 TB. Батарея: 7 циклів. Статус MDM не перевіряли.",
  "offers": {"price": "65000", "priceCurrency": "UAH"},
  "image": "https://shop.example/media/42.jpg"
}
</script>
<section>
  Розпакований. M5, 24 GB RAM, SSD 1 TB. Батарея: 7 циклів.
  Статус MDM не перевіряли.
</section>
```

### Кандидати

```text
b0 → JSON-LD Product із назвою, URL, описом, offers та image
b1 → можливий DOM-кандидат із видимим описом і характеристиками
```

Routing обирає придатний кандидат і стратегію. Конкретний набір кандидатів
і план залежать від builder, схеми та режиму. У прикладі опис є в самому
JSON-LD, тому enrichment кандидата `b0` має потрібні докази; якщо опис був
би тільки у DOM, він не потрапив би в запит для `b0` автоматично.

### Структурована основа та доповнення

```json
{
  "title": "MacBook Air M5 24GB / 1TB, Open Box",
  "url": "https://shop.example/item/42",
  "price": 65000,
  "currency": "UAH"
}
```

Commerce/DOM-правила можуть уже витягнути частину характеристик. Якщо вони
залишилися відсутніми, LLM отримує обмежений опис і схему потрібних доповнень:

```json
{
  "chip": "M5",
  "ram_gb": 24,
  "ssd_gb": 1024,
  "condition": "open_box",
  "battery_cycles": 7,
  "mdm_status": null
}
```

Назви полів, кодування стану й одиниці задаються конкретною схемою. Число
1024 тут припускає, що схема визначає саме таке нормалізоване представлення
1 TB; універсального конвертера всіх одиниць і валют у ядрі немає.

### Фінальний envelope

```json
{
  "record_id": "source-derived-id",
  "job_name": "example-laptop-monitor",
  "img_url": "https://shop.example/media/42.jpg",
  "data": {
    "title": "MacBook Air M5 24GB / 1TB, Open Box",
    "url": "https://shop.example/item/42",
    "price": 65000,
    "currency": "UAH",
    "chip": "M5",
    "ram_gb": 24,
    "ssd_gb": 1024,
    "condition": "open_box",
    "battery_cycles": 7,
    "mdm_status": null
  },
  "provenance": {
    "page_id": "snapshot-id",
    "source_url": "https://shop.example/item/42",
    "candidate_ids": ["b0"],
    "extractor": "json_ld+openrouter",
    "snapshot_ref": "data/snapshots/snapshot-id.html",
    "model": "qwen/qwen3.7-flash",
    "prompt_version": "extraction.v3",
    "identity_basis": "entity_url"
  }
}
```

У реальному run candidate IDs/provenance відповідають фактично використаним
доказам. Поля моделі та extractor не додаються як твердження про AI, якщо
конкретний запис оброблено лише детермінованим кодом.

## 7. Які зовнішні запити реально виконуються

| Операція | Куди йде запит | Що повертається |
| --- | --- | --- |
| Fetch сторінки | HTTP(S) сайт або браузерна сесія | HTML/DOM та status |
| Генерація/уточнення схеми | OpenRouter chat completions | Обмежений план полів |
| Query planning | OpenRouter chat completions, якщо ввімкнено AI | Варіанти web query та site search |
| Web search | OpenRouter chat completions із `openrouter:web_search` | Пошукові citations і usage |
| Native Decisions | OpenRouter `/api/alpha/decisions` | Відповіді на іменовані питання/вибір дій або блоків |
| LLM extraction | OpenRouter `/api/v1/chat/completions` | Структурований JSON для schema validation |
| Зображення у UI | Браузер користувача → URL джерела | Файл зображення або помилка/fallback |

Це інтеграція **через OpenRouter**, а не прямий OpenAI SDK-клієнт.
Моделі конфігуровані; у поточних профілях extraction —
`qwen/qwen3.7-flash`, routing/navigation — `openai/gpt-6-luna-decisions`.
Ці назви описують конфігурацію проєкту, не обіцянку майбутньої доступності.

Для Qwen у `response_mode: auto` використовується `json_object` зі схемою
в prompt і локальною перевіркою. Для інших підтримуваних chat-моделей auto
може обрати `json_schema`. Native Decisions має окремий контракт
`state + questions → answers`, а не генерує довільний record JSON.

Не кожна сторінка створює всі ці запити. Фіксована схема виключає її
генерацію, передані джерела виключають discovery, rules зменшують Decisions,
структуровані факти зменшують enrichment, cache може усунути повторний API-виклик.

`--no-ai` вимикає inference, але в `discover` сам платний web search може
залишитися з literal query. Для сценарію без web search слід передати
джерела через `search --source` або запускати відповідний job/replay.

## 8. Оптимізація витрат

Реалізовано кілька незалежних механізмів:

1. Структуровані дані й DOM використовуються перед дорогим повним extraction.
2. Hybrid routing не викликає Decisions для строго визначеного простого випадку.
3. AI бачить обмежені блоки/evidence замість необмеженого HTML.
4. Sparse enrichment повертає відсутні або конфліктні поля.
5. Optional reasoning можна вимкнути; output tokens обмежені.
6. AI cache прив'язаний до моделі, prompt/schema, джерела та evidence.
7. Пошукова видача має окремий TTL cache.
8. Всі етапи та retries ділять `max_calls`.
9. Durable response spool дозволяє відтворювати підтверджені відповіді після збою.
10. Incremental mode пропускає завершені деталі до fetch і AI.

### Підтверджений benchmark

Однаковий корпус із **п'яти збережених OLX-сторінок**:

| Метрика | Baseline | Оптимізований cold replay |
| --- | ---: | ---: |
| AI calls | 10 | 5 |
| Local cache hits | 0 | 0 |
| Input tokens | 30 883 | 7 460 |
| Output tokens | 20 026 | 548 |
| Estimated token cost | $0.00468627 | $0.00029504 |

Зниження **оціненої за токенами** вартості — **93.704%**. Перевірено
52 source-reviewed quality invariants та збереження тих самих п'яти record IDs.
Окремий warm replay мав 0 нових calls і 5 cache hits.

Для optimized cold provider повідомив $0.0003044885. Actual billing baseline
неповний/невідомий, тому не можна називати 93.704% доведеним зменшенням
фактичного рахунку. Також це не універсальний результат для інших сайтів,
схем чи обсягів і не оцінка browser/storage/hosting витрат.

Безпечна CV-фраза: «Зменшив оцінену AI-вартість на 93.7% на фіксованому
п'ятисторінковому benchmark, зберігши 52 перевірені інваріанти якості».
Особисте авторство цієї оптимізації потрібно підтвердити окремо.

Докази та методика: [cost-optimization.md](cost-optimization.md).

## 9. Облік вартості та контрольована зупинка

В UI показується сума вартості з отриманих provider usage metadata. Вона
зростає після завершених відповідей, а не за таймером. Система розрізняє:

- Відому суму: `known_cost_usd`.
- Повноту обліку: `cost_complete`.
- Спроби без cost metadata: `cost_pending_calls`.
- Запити в польоті: `in_flight_calls`.
- Повний `cost_usd`, лише коли повнота підтверджена.

Невідома вартість не видається за нуль. Cache-only run може мати нуль нових
витрат, але це не означає, що початкове наповнення cache було безкоштовним.

Кнопка «Зупинити» скасовує run, закриває ресурси та зберігає готові записи.
Відмова провайдера через доступні кредити переводить весь запуск у
контрольований `stopped`, а не породжує помилку extraction для кожної
наступної сторінки. Тимчасове обмеження одночасних витрат відрізняється
від підтвердженого нульового балансу. Система не опитує баланс як універсальний
preflight перед кожною дією; реакція спирається на відповіді провайдера.

## 10. Захист від збоїв і три різні режими повторної роботи

### `resume`: продовжити той самий run

Зберігає ID, бюджет та контекст незавершеного запуску. Checkpoint містить
записи, плани, завершені кандидати/сторінки та стан обходу. Фактичні моделі
й схема фіксуються, щоб зміна `.env` не підмінила обробку посеред відновлення.

Прийнятий запис зберігається під час роботи у per-run checkpoint та локальний
DatasetStore. Live-подія запису надходить після цього шляху commit. Фінальні
експорти й звіт формуються окремо. Це уточнює старі фрагменти документації,
де persistence описувалася лише наприкінці запуску.

Є OS-held leases, транзакції SQLite, синхронізація обов'язкових записів
на диск, атомарна публікація файлів та обробка пошкодженого хвоста журналу.
Браузерна сесія в пам'яті після завершення процесу не зберігається: потрібну
спостережену адресу відкривають знову, а action binding перевіряють за новим
станом. Небезпечне повторне натискання застарілого selector не виконується.

### Durable usage journal: не оплачувати сліпо повторно

Перед HTTP-запитом фіксується intent. Отримана відповідь зберігається в
окремому response spool до подальшого parse/cache. Підтверджений результат
можна використати при resume навіть із вимкненим optional AI cache.

Якщо процес завершився після відправлення, але до збереження відповіді,
провайдер міг уже списати кошти. Система позначає outcome як unknown і
не повторює такий запит автоматично. Це **захист від сліпого повторного
білінгу**, а не математична exactly-once гарантія зовнішнього сервісу.

Помилка обов'язкового запису на диск зупиняє нові платні дії. Захист не
замінює backup диска та не створює спільну distributed transaction між
SQLite, PostgreSQL і файловими export artifacts.

### `reprocess`: новий run зі збережених HTML

Повторно обробляє snapshots без нового crawling і web search. Використовує
збережену ефективну схему; генерація/уточнення не повторюються. Без
`--no-ai` extraction може знову звернутися до провайдера, якщо немає
придатного cache. Це спосіб змінити обробку вже отриманих доказів.

### `update` / incremental: дозібрати нові деталі

Створює **новий run** із попереднім питанням, схемою та збереженими джерелами.
У `update` не запускаються новий web search і генерація схеми.
Старі дані залишаються; нова вибірка є delta, а UI має посилання на батьківську.

`data/incremental.sqlite` зберігає завершені detail URL. Ключ включає job,
питання, ефективну схему, фактичні моделі, предметні/extraction налаштування
та значущі evidence caps. Зміна контексту не повинна приховувати дані,
які треба обробити заново. Джерела й звичайні crawl limits не скидають
контекст автоматично.

```text
Новий каталог містить A, B, C
        ↓
Ledger: A і B мають підтверджене durable completion
        ↓
A/B пропускаються до HTTP, browser і AI
C відкривається, обробляється та зберігається
```

Каталоги, пошук і пагінація перечитуються — інакше не можна знайти C.
Помилки, 403, незавершений extraction і card-only спостереження не роблять
detail URL завершеним. Відомі елементи прибираються **до** обмежень inventory
та candidate budget, щоб старі A/B не витіснили новий C. Пагінація й lazy
continuation залишаються доступними навіть після відкидання всіх старих карток.

Перед довірою до processed completion перевіряються активні записи. Карантин
або вилучення запису робить деталь доступною для повторної обробки.
Для ручної зміни активного запису зі збереженим ID потрібна явна invalidation
або повний запуск. Scope lease запобігає конкурентному дозбору одного контексту.

Для старих запусків застосовується консервативна міграція: потрібні schema/
admission checks, власна detail-сторінка та збережені докази, а не лише факт
колишнього відвідування. Початкова перевірка великої старої вибірки може
тривати хвилини; вона винесена з API event loop і підтримує скасування.

Incremental **не перевіряє нову ціну вже готового оголошення**. Для refresh
існуючих даних потрібен звичайний запуск із `--no-incremental`.
Після crash спочатку слід використовувати `resume`, щоб зберегти семантику
бюджету та журналу незавершеного run.

Докладно: [recovery.md](recovery.md), [incremental.md](incremental.md).

## 11. Сховища, provenance та артефакти

### Сховища

- SQLite — основний локальний датасет, runs, current records, history й assessments.
- Окремий per-run SQLite checkpoint — прогрес і відновлення виконання.
- Окремий SQLite incremental ledger — міжзапускові завершені detail URL.
- PostgreSQL через `psycopg` — необов'язкова додаткова persistence-копія.
- Файлова система — snapshots, manifests, responses, audit logs та exports.

JSONL зберігає повний envelope. Parquet/CSV виносять доменні поля на верхній
рівень, а службові метадані — у зарезервовані колонки `_record_id`, `_job_name`,
`_source_url`, `_provenance_json`, `_assessments_json`, `_img_url` та часові поля.
Arrow/Parquet зберігає однорідні scalar types; вкладені чи змішані значення
кодуються JSON із відповідною metadata. DuckDB залежністю проєкту не є.

### Provenance кожного запису

Містить source URL, page/snapshot ID, candidate IDs, extractor,
snapshot reference, а для AI — модель і версію prompt. Identity basis
пояснює, на чому побудована ідентичність запису.

Це record-level provenance: він показує, які сторінка та блоки використані
для запису. Автоматичної окремої lineage-мапи для кожного поля немає.
Конкретне значення можна перевірити у вихідному HTML і повторити extraction
без crawling.

### Типові файли run

| Артефакт | Для чого потрібен |
| --- | --- |
| `job.json` | Конфігурація й схема запуску |
| `schema.json` | Ефективний контракт записів |
| `schema-generation.json`, `schema-evidence.json` | План полів і докази уточнення, якщо auto-schema активна |
| `discovery.json` | Запити, citations, джерела й site search, якщо є discovery |
| `pages.jsonl` | Manifest snapshots і ролей сторінок |
| `navigation.jsonl` | Дії, стани, плани й причини зупинки |
| `routing.jsonl` | Вибір блоків, стратегії та доступні model probabilities |
| `admission.jsonl` | Пояснення accepted/review/rejected |
| `rejected-records.jsonl` | Оригінали відхилених записів |
| `checkpoint.sqlite` | Durable стан для resume |
| `records.jsonl`, `records.parquet`, CSV | Результати відповідно до outputs |
| `summary.json` | Статус, counters, coverage, usage, errors, artifacts |

Артефакти конкретних етапів можуть бути відсутні, коли етап вимкнений.
Локальний `data/` ігнорується Git. Snapshot references можуть бути локальними
шляхами; переносити лише manifest без HTML недостатньо для replay.

## 12. Вебінтерфейс і API

Frontend — **HTML, CSS і vanilla JavaScript ES modules**, які обслуговує
FastAPI. React, Vue, TypeScript і окремий frontend build framework тут не
використовуються. Структура UI розділена на transport, state, views, results,
filters, dialog, cost та actions; стилі — на окремі CSS-модулі.

### Live flow

```text
Форма → POST /runs → 202 + run_id
                         ↓
              supervised asyncio task
                         ↓
                 той самий PipelineRunner
                         ↓
     stage / records / counters / usage / logs
                         ↓
             GET /runs/{id}/events (SSE)
                         ↓
               оновлення UI без reload
```

SSE має reconnect; є snapshot fallback і захист від старих revisions.
Закриття вкладки не скасовує збір. Повернення через `/?run=<id>` відновлює
перегляд. Типово активний один UI-run; місткість явно налаштовується,
але зовнішньої distributed queue немає.

UI показує картки або таблицю, фото, деталі, колонки, history, progress,
warnings/errors, фактичний стан збереження та накопичену вартість. Є
зупинка, resume, update і JSON download.

### Автоматичні колонки й фільтри

Модель може запропонувати типи, підписи, одиниці, display roles і порядок
колонок під час побудови/уточнення схеми. Backend рахує presentation metadata
за реальною вибіркою. Frontend детерміновано відображає її, а не викликає
AI для кожного render або зміни фільтра.

- Number/integer: діапазони за фактичними min/max.
- Boolean: фактичні так/ні з окремим невідомим значенням.
- Низькокардинальні рядки: категорії та кількості.
- Рядки з багатьма значеннями: текстовий пошук.
- Date/date-time: діапазони дат.
- Arrays: пошук у представленні значень; objects — деталі.

`0` і `false` не прирівнюються до missing. Умови поєднуються через AND.
Ліміти й категорії рахуються за поточною вибіркою, до застосування локальних
фільтрів. Діагональ може бути категорією, якщо схема оголосила її рядком;
числове поле не перетворюється автоматично на категоріальне лише через
три значення. Можна вручну обирати колонки без нового AI-запиту.

### Основні endpoints

```text
GET  /health
GET  /jobs
POST /runs
GET  /runs
GET  /runs/{id}
GET  /runs/{id}/events
POST /runs/{id}/cancel
POST /runs/{id}/resume
POST /runs/{id}/update
GET  /records
GET  /records/{record_id}/history
POST /jobs/{job_id}/run
```

Фоновий `POST /runs` відрізняється від endpoint запуску готового job, який
очікує фінальний результат. OpenAPI доступна через FastAPI.

## 14. Приклади команд

```powershell
# Встановлення з browser backend
uv sync --dev --extra browser
uv run playwright install chromium

# Перевірити конфігурацію
uv run unified-parser validate configs/jobs/macbooks.yaml

# Питання → web search → сайти → автоматична схема → датасет
uv run unified-parser discover "Знайди вакансії Python. Збери назву, компанію, зарплату, місто та URL."

# Почати з конкретного сайту
uv run unified-parser search "MacBook M5" --source https://www.olx.ua/ --config configs/jobs/macbooks-m5-complete.yaml

# Запуск готового профілю
uv run unified-parser run configs/jobs/macbooks-m5-complete.yaml

# Продовження незавершеного запуску
uv run unified-parser resume RUN_ID --max-pages 1000

# Новий дозбір завершеного запуску
uv run unified-parser update RUN_ID --data-dir data

# Incremental для job
uv run unified-parser run configs/jobs/macbooks-m5-complete.yaml --incremental

# Повторне читання існуючих сторінок, наприклад для refresh цін
uv run unified-parser run configs/jobs/macbooks-m5-complete.yaml --no-incremental

# Повторний deterministic extraction із локальних snapshots
uv run unified-parser reprocess configs/jobs/macbooks.yaml --from-run data/runs/RUN_ID --no-ai

# Експорт current dataset
uv run unified-parser export macbook-monitor --format parquet --output data/exports/macbooks.parquet

# API та UI
uv run unified-parser serve --host 127.0.0.1 --port 8001
```

`RUN_ID` та назва job в export — placeholders або приклади; вони повинні
відповідати наявним локальним даним. Встановлення потребує налаштованого
середовища, а AI/discover — відповідного ключа та доступних API-кредитів.

## 15. Реальний MacBook-кейс і підтверджені результати

Тестовий кейс виник із потреби знайти MacBook M5 Air/Pro у конфігураціях
16/512, 16/1TB і 24/1TB, у стані «як новий»/розпакований, із невеликою
кількістю циклів та зрозумілим статусом MDM. Це був драйвер розвитку
універсального pipeline, а не причина зашити всі поля ноутбука в core.

### Історична агрегована вибірка

Run: `5139fffa2def484189360755cadb2fbb`.

- Початково 593 записи в агрегованому наборі.
- Після перевірки: 109 явно відхилених, 11 неоднозначних винесено окремо,
  473 підтверджених за правилами цього очищення залишено у вибірці.
- 471 із 473 має підтверджене посилання на фото.
- Для двох решти джерело під час recovery повертало HTTP 410.
- Паралельна збережена вибірка-кандидат `310ad6c94e98436cb70101481488f26f`
  має 30 записів і 30 фото; це не обов'язково 30 додаткових унікальних
  пристроїв понад 473, тому числа не можна механічно складати.

Прийняті записи фактично походять із п'яти хостів: OLX — 315,
Swipe — 87, Skay — 59, iStory — 8, Setuply — 4. Сім налаштованих джерел
не означають сім джерел із прийнятими результатами.

Агрегат збирався з кількох запусків, а очищення/доповнення зображень
виконувалося окремою ремонтною процедурою зі збереженням оригіналів.
Це не «один безпомилковий autonomous run знайшов усі MacBook в Україні».
Підтвердження предмета оголошення не гарантує відповідності всіх 473
вузькому списку конфігурацій, стану, циклів і MDM. Для цього потрібні
окремі перевірки полів та ручне уточнення невідомого.

### Дозбір для старого агрегату

Під час read-only перевірки використовувався тимчасовий incremental ledger:
360 detail URL отримали достатнє підтвердження завершеної обробки,
113 записів не були перенесені як готові та залишаються придатними до
повторного читання/доповнення. Тимчасовий ledger видалено; сама перевірка
не запускала новий crawling або платний AI та не змінювала реальний датасет.
Результат зафіксований у console output робочої сесії; окремого збереженого
benchmark artifact для цієї міграції немає.

Це результат консервативної міграції саме цієї старої вибірки, а не
твердження, що 113 записів є новими оголошеннями або помилками.

Великий M5-кейс має $0.0725473465 відомих usage-витрат, але
`cost_complete=false`: частина історичного перерваного збору не залишила
повного billing. Отже, не можна писати «473 записи зібрано за $0.073».
Повторна локальна assembly/repair-процедура не додала платних AI-викликів.

### Інші перевірені сценарії

- Books to Scrape: root → категорія Travel → три книги; п'ять сторінок,
  три записи. Один збережений live-run використовував новий AI call і cache;
  не слід називати його cold/no-AI benchmark. Rules/no-AI запуск підтримується окремо.
- Загальна документація Python: одна сторінка й один запис за некомерційною
  схемою, без помилок; окремий приклад виходу за межі товарного кейсу.
- Локальні HTTP і справжній Chromium: GET/JS search, select, load-more,
  scroll, pagination та delayed/lazy results.
- Історичні live/replay перевірки OLX, Prom, Rozetka; також були 403/429,
  partial та нерелевантна пошукова видача. Успішний fetch не доводить relevance.
- Контекстне уточнення схеми на трьох збережених OLX-сторінках із реальним
  Qwen: п'ять API calls, три записи, без errors/warnings; це replay-like
  AI-перевірка на snapshots, не новий web search.

Джерела: [live-validation.md](live-validation.md),
[schema-generation.md](schema-generation.md), [data-quality.md](data-quality.md).

## 16. Тестування й контроль якості

Остання повна перевірка поточного коду в цій робочій сесії:
**936 pytest tests passed**, без warnings у фінальному прогоні;
окремо **16 Node frontend tests passed**, синтаксична перевірка 12 JS-файлів,
Ruff lint і format check пройшли. Ці числа зафіксовані у terminal output
сесії, а не у committed CI badge або окремому версійованому test report.

Покрито, зокрема:

- Конфігурації, auto-schema, типи, mappings та validation.
- JSON-LD/DOM/LLM routing і enrichment, відсутні поля та conflicts.
- Прив'язку зображення до конкретної сутності.
- Identity, merge/upsert, change history та exports.
- Правильне відокремлення аксесуарів і неправильних моделей.
- HTTP/browser navigation, форми, pagination, JS controls та resource lifecycle.
- Спільні бюджети, cache, retries, usage metadata та кредитну зупинку.
- Resume, usage journal, збережені відповіді й ambiguous paid outcomes.
- Incremental context isolation, незавершені деталі, quarantine invalidation.
- Старі A/B перед новим C при малих candidate/action limits.
- Продовження pagination/lazy results після пропуску всіх старих карток.
- Live API, SSE snapshots, cancellation, history та UI filters.

Незалежні incremental integration tests використовували справжній локальний
HTTP-сервер зі змінним каталогом. Перший run мав A/B, наступний — B/C;
підтверджено повторне читання каталогу та fetch/extraction лише нового C.
Помилки HTTP/LLM, зміна контексту та quarantine перевірялися окремо.

Live UI перевірено headless Chromium на desktop 1440 px і mobile 390 px:
кнопка update, один POST на клік, відсутність автоматичного POST при відкритті,
delta records і parent link, відсутність JS errors/горизонтального overflow.
Під час цього UI smoke POST був перехоплений тестом, тому реального нового
MacBook-збору та платних запитів не виконувалося.

Тести використовують локальні fixtures/mock transports там, де не потрібен
справжній browser/HTTP. Окремі live benchmarks і перевірка PostgreSQL мають
власні умови запуску й не повинні називатися повністю оплаченими/виконаними
заново лише тому, що пройшов pytest.

У pytest `DeprecationWarning`, `PendingDeprecationWarning` і `FutureWarning`
перетворюються на помилки. Це механізм виявлення deprecated-використань,
а не гарантія відсутності всіх можливих майбутніх deprecations.

## 17. Що є інженерною цінністю для резюме

1. **Schema-driven design:** довільні предметні записи без MacBook-моделі в core.
2. **Pipeline-first modularity:** одна бізнес-логіка для CLI, API, UI та replay.
3. **Grounded autonomous navigation:** AI обирає лише реально спостережені дії.
4. **AI-assisted extraction:** локальні факти плюс обмежений LLM enrichment.
5. **Typed contracts:** Pydantic для повідомлень і JSON Schema для даних.
6. **Cost engineering:** guarded fast paths, sparse output, cache й спільні budgets.
7. **Durable execution:** checkpoint, OS lease, recovery та збереження records під час роботи.
8. **Billing-aware recovery:** intent/response journal та захист від сліпого retry.
9. **Incremental crawling:** пропуск завершених detail URL до HTTP/AI з context isolation.
10. **Data quality:** admission, quarantine, точна прив'язка фото та audit trail.
11. **Data engineering:** transactional upsert, change history, typed Parquet і JSONB persistence.
12. **Live product interface:** SSE, автоматичні filters/columns, usage та cancellation.
13. **Verification:** великі unit/integration suites та відтворюваний cost benchmark.

Це можна позиціонувати як Backend/Python, Data Engineering або Applied AI
проєкт залежно від вакансії. ML Research, training власних моделей чи
досвід масштабування production-кластера цей код сам по собі не підтверджує.

## 18. Чого не слід приписувати проєкту

- Гарантованого парсингу будь-якого сайту або збору абсолютно всіх результатів.
- Автоматичного обходу captcha, login/authorization та антибот-захисту.
- Реалізованого універсального robots.txt enforcement або автоматичної
  перевірки всіх правил доступу сайту.
- Повної відсутності hardcoded логіки: є загальні евристики, semantic mappings
  і явно ввімкнені domain rules. Немає потреби зашивати search path кожного сайту.
- Універсальної конвертації всіх валют і одиниць або підтвердженої ринкової ціни.
- Гарантованого MDM/стану батареї чи каліброваного fraud/deal score.
- Абсолютної відсутності втрат за будь-якої відмови диска.
- Exactly-once платежів сторонньому API або distributed transactions.
- Мільйонів записів, production throughput чи навантажувального SLA без вимірювань.
