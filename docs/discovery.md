# Питання → пошук сайтів → датасет

`discover` приймає питання без списку джерел. JSON Schema визначає поля результату;
без `--config` поля й схема [автоматично створюються з питання](schema-generation.md),
а runtime-ліміти беруться із загального профілю [web.yaml](../configs/jobs/web.yaml).
Для RAM, SSD, MDM та інших характеристик є [macbooks-web.yaml](../configs/jobs/macbooks-web.yaml).
Типовий content profile — `generic`: немає вимоги ціни чи валюти для запису.
Товарні профілі, валютні aliases й вибір JSON-LD types описані в
[domain-profiles.md](domain-profiles.md); вони не вмикаються лише через назви полів схеми.

```powershell
uv run unified-parser discover "Знайди MacBook Air 15 M4 24GB у продажу в Україні" --config configs/jobs/macbooks-web.yaml --search-results 3 --pages-per-site 4
uv run unified-parser discover "Книги про подорожі ціна" --search-results 5 --pages-per-site 3
uv run unified-parser run configs/jobs/macbooks-web.yaml
```

Потрібен `OPENROUTER_API_KEY` у `.env`. Для browser-профілів також потрібні
`uv sync --dev --extra browser` та `uv run playwright install chromium`.

## Шлях даних

```text
Питання → автоматична схема (або явно обрана готова схема)
  → Qwen: кілька варіантів запиту і рядок для пошуку всередині сайтів
  → OpenRouter Web Search Server Tool: обмежений пошук для кожного варіанта
  → URL, заголовки й уривки з provider annotations
  → об'єднання доменів за всіма запитами, ліміт max_sites
  → корінь кожного унікального сайту
  → чистий внутрішній пошук → результати → картки та пагінація
  → JSON-LD / DOM / LLM → валідація схеми
  → спільний SQLite/PostgreSQL dataset + JSONL/Parquet
```

Модель планувальника формує запити, а не адреси сайтів. Наприклад, із питання
«Знайди MacBook Air 15 M4 24GB у продажу в Україні» може вийти:

```json
{
  "queries": [
    "MacBook Air 15 M4 24GB купити Україна",
    "MacBook Air 15 M4 24GB оголошення Україна",
    "MacBook Air 15 M4 24GB інтернет-магазин Україна"
  ],
  "site_search": "MacBook Air 15 M4 24GB"
}
```

Це ілюстрація контракту, а не запис конкретного запуску. Типовий режим
`entrypoint: site_root` починає з кореня знайденого сайту, навіть якщо web search
повернув картку чи відфільтрований каталог. Далі використовуються
[спостережувані форми, категорії та посилання](navigation.md).
`entrypoint: result_url` дозволяє починати зі знайдених сторінок, як у попередній версії:
у цьому режимі зберігаються різні URL одного сайту, а `max_sites` обмежує кількість сайтів.

URL беруться виключно з `message.annotations[].url_citation`, не з тексту відповіді
моделі. `search_results` — максимум URL на один пошук, а `max_sites` — спільна межа
унікальних сайтів. Кожен запланований запит виконується в межах спільного бюджету,
навіть якщо попередній уже заповнив свою видачу. Результатів може бути менше за ліміт.
Server Tool повертає citations; їхній порядок не є документованим глобальним SERP rank.

Наприклад, URL `https://www.shop.example/products/42?ram=24` і
`https://shop.example/search?q=MacBook` дають один сайт і один стартовий URL:
`https://www.shop.example/`. Зберігається origin першого знайденого URL, щоб не
вигадувати доступність домену без `www` чи спеціалізованого піддомену.
Ідентичність сайту визначається за зареєстрованим доменом через локальний Public Suffix
List; різні орендарі приватних суфіксів, наприклад `alice.github.io` та `bob.github.io`,
залишаються різними сайтами. Завантаження PSL із мережі вимкнене.

Кожен сайт стає одним початковим джерелом у site-root режимі. Усередині нього може
бути багато переходів. Повторні товари перевіряються окремою дедуплікацією записів:
однакові моделі в різних продавців можуть бути різними пропозиціями.

## Ліміти

```yaml
sources: []
search: Знайди MacBook Air 15 M4 24GB у продажу в Україні
discovery:
  enabled: true
  query_mode: ai
  max_queries: 3
  search_results: 25
  max_sites: 25
  entrypoint: site_root
  pages_per_site: 5
  engine: parallel
  mode: basic
  search_context_size: low
  cache_ttl_seconds: 3600
crawl:
  max_pages: 125
  max_records: 100
ai:
  max_calls: 100
```

- `search_results`: 1–25 URL на кожен запит. CLI: `--search-results`.
- `max_queries`: кількість варіантів запиту; типово три в загальному профілі.
  CLI: `--max-queries`. Literal mode виконує один початковий запит.
- `max_sites`: максимум унікальних сайтів у site-root режимі. CLI: `--max-sites`.
- `entrypoint`: `site_root` або `result_url`. CLI: `--entrypoint`.
- `search_context_size`: `low` / `medium` / `high`, типово `low`.
  CLI: `--search-context-size`. Визначає обсяг контексту пошуку, не кількість посилань.
- `pages_per_site`: ліміт спроб на сайт, спільний для піддоменів одного
  зареєстрованого домену. Включає browser-взаємодії.
- `crawl.max_pages`: загальний ліміт спроб обходу всіх джерел. Пошукові API-виклики
  рахуються окремо в `ai.max_calls`.
- `crawl.max_records`: загальний ліміт записів. Досягнення ліміту може завершити
  запуск до відвідування всіх знайдених URL.
- `ai.max_calls`: спільний бюджет schema generation, planning, web search, navigation, routing та
  extraction, включно з retries. Cache hits його не витрачають.

Загальний профіль має 125 спроб сторінок, 100 записів і 100 AI attempts: це дає
25 сайтам по п'ять спроб, якщо інші ліміти не завершать запуск раніше. Спочатку кожне
джерело отримує чергу на відкриття; це не означає завершення обходу кожного джерела.
Для короткого тесту явно зменшуй `--max-sites`, `--max-pages`, `--max-records`
і `--max-calls`. Бюджет викликів не є грошовим лімітом.

Для `discover` джерела з обраного профілю очищаються. Для YAML `run` можна явно
поєднати `sources` і ввімкнений `discovery`. Помилка пошуку не підміняється
непомітним запуском старого списку сайтів.

За замовчуванням `navigation.allow_filters: false`: пошук не додає цінові,
характеристичні чи географічні фільтри та не перемикає сортування. Увімкнення:
`--allow-filters` або відповідне поле YAML. Категорії, текстовий пошук і пагінація
залишаються доступними. Це не обхід обмежень сайту: приховані серверні налаштування,
cookies або геолокація можуть впливати на видачу незалежно від URL і форми.

Точний варіант із питання користувача:

```powershell
uv run unified-parser discover "Знайди MacBook Air 15 M4 в Україні. Збери назву, URL, ціну, RAM і SSD." --max-queries 3 --search-results 25 --max-sites 25
```

Дешевша видача з тим самим обходом:

```powershell
uv run unified-parser discover "MacBook Air 15 M4 в Україні" --max-queries 3 --search-results 10 --max-sites 25
```

## Витрати й кеш

Типово використовується OpenRouter Web Search Server Tool з `parallel/basic`: один пошук
до 10 результатів коштує $0.005 за тарифом сервісу на момент реалізації,
додатково оплачуються токени моделі. Кожен результат понад перші десять коштує
ще $0.001: пошук із 25 результатами — $0.02, три таких пошуки — $0.06 плюс токени.
Три пошуки по десять результатів — $0.015 плюс токени. `parallel/fast` коштує $0.001 за пошук,
але документація не визначає його мовне покриття. `exa/auto` — $0.007 за пошук
до 10 результатів. Поточні тарифи й режими:
[офіційна документація OpenRouter](https://openrouter.ai/docs/guides/features/server-tools/web-search).

## Контракт Server Tool

Використовується той самий `POST /api/v1/chat/completions`, але запит містить
`tools` замість deprecated `plugins`. Для кожного варіанта плану код передає:

```json
{
  "tools": [
    {
      "type": "openrouter:web_search",
      "parameters": {
        "engine": "parallel",
        "mode": "basic",
        "max_results": 25,
        "max_total_results": 25,
        "max_uses": 1,
        "search_context_size": "low"
      }
    }
  ],
  "tool_choice": "required",
  "max_tool_calls": 1
}
```

Це фрагмент запиту: модель і повідомлення додаються окремо. Єдиний доступний інструмент —
web search. `tool_choice: required` вимагає використання інструмента, а `max_uses`
та `max_tool_calls` обмежують його виконання. `max_total_results` обмежує загальну
кількість результатів усередині одного API-запиту. Після відповіді код додатково
перевіряє **строго цілий лічильник одного фактичного пошуку** у usage.

Підтримуються `usage.server_tool_use_details.web_search_requests` (фактичний Chat API)
і `usage.server_tool_use.web_search_requests` (приклад у документації). Суперечливі
лічильники, нуль, відсутнє підтвердження або більше одного пошуку повертають помилку,
а не успішну пошукову видачу. Звичайні URL у тексті моделі не стають джерелами.
Токени й відому вартість відповіді враховуємо і при відхиленні її результату.
Повернення до старого плагіна при помилці не виконується.

Server Tool дозволяє моделі сформулювати власний пошуковий query. Prompt просить
зберегти заплановану фразу та її умови, але Chat API не гарантує повернення виконаного
query. У журналі зберігається запланований запит; його не слід трактувати як доказ
буквально незмінного тексту, переданого пошуковому провайдеру.

Ліміт одного пошуку діє на окрему HTTP-спробу. Наявні bounded retries для мережевих
помилок і transient HTTP statuses можуть повторити її та витратити додатковий бюджет.
Кожна HTTP-спроба враховується у спільному `ai.max_calls`; гарантії exactly-once billing
після невідомого результату мережевого запиту немає.

Пошуковий кеш має TTL, типово одну годину. Це окремо від кешу структурованих
AI-відповідей. Повторний обхід може використати ту саму видачу в межах TTL,
але знову завантажує сторінки сайтів. Після TTL виконується свіжий пошук.
Міграція має окрему версію кешу: видача старого плагіна не підміняє результат
Server Tool. Розмір контексту та обмеження пошуку включено в cache identity.
Поточна версія `web-search.v4-server-tool` також використовує актуальний параметр
`max_completion_tokens`. Старий v3-кеш із `max_tokens` не приймається: перше звернення
за новим контрактом виконає новий запит; наступні можуть використати кеш у межах TTL.
Cache hit не виконує нового пошуку й не додає його до мережевого usage.
У `query_outcomes` поле `web_search_requests` показує лічильник прийнятої відповіді
або нуль для cache hit; `original_web_search_requests` зберігає початкове підтвердження.
У stage stats `reported_web_search_requests` — сума відомих лічильників. Загальне
`web_search_requests` не показується, якщо після мережевих retries не всі HTTP-спроби
мають перевірений usage: невідома вартість попередньої спроби не прирівнюється до нуля.

`--query-mode literal` передає рядок без AI-планування. Для нової auto-schema потрібен AI;
з `--no-ai` використовуй `--fixed-schema` чи явно обраний фіксований профіль.
У режимі фіксованої схеми `--no-ai` вимикає
планування та AI-обробку сторінок, але **пошук через OpenRouter усе одно платний**:
Server Tool працює через модель. Для нього потрібні ключ і ненульовий бюджет викликів.
Якщо планувальник повернув невалідну відповідь, виконується один контрольований
fallback на початковий рядок без другого AI-запиту планування. У звіті залишаються
warning, причина й `effective_query_mode: literal_fallback`.

`ai.cost_usd` показує лише повернуті провайдером cost metadata. Ми не вигадуємо
нульову ціну за відсутності метаданих і не гарантуємо, що usage metadata окремого
запиту відображає всі сервісні доплати. Перевіряй також OpenRouter Activity.

## Аудит і межі

У каталозі запуску `discovery.json` зберігає питання, запити, повернуті результати
і вибрані джерела, об'єднані сайти та зв'язок із пошуковими URL;
`navigation.jsonl` — фактичні дії crawler;
`summary.json` — записи, помилки, ліміти й usage.
У `query_outcomes` видно успіх або помилку кожного пошукового запиту;
збій наступного запиту не втрачає джерела, уже знайдені попереднім.
`site_attempts` і `source_outcomes` показують обхід та зупинки по сайтах/джерелах.

`reprocess` працює зі збереженими сторінками й не повторює пошук джерел;
за ввімкненого AI extraction може мати власні запити.

Наявність URL у пошуку не означає доступності сторінки або відповідності товару
всім умовам питання. CAPTCHA, недоступні сторінки й помилки extraction залишаються
видимими у звіті. Довільні характеристики задаються готовою або автоматично створеною
схемою. Генерація схеми не запроваджує довільні жорсткі фільтри за умовами питання.
Для `is_relevant` discovery-run використовує короткий `site_search`, а не службові
слова повного питання. Це наявне зіставлення токенів, а не повна семантична перевірка
країни, бюджету й усіх умов питання; у literal mode фраза залишається початковою.
Кілька запитів і дедуплікація сайтів розширюють охоплення, але не гарантують знаходження
всіх сайтів інтернету, обходу всіх вибраних сайтів у межах лімітів чи всіх їхніх товарів.

автоматичних повторів з іншою формою або старим плагіном немає.

Питання → схема → query planning → Server Tool (actual web_search_requests=1)

## Історична перевірка site-root discovery

Ці traces отримані до міграції Server Tool через попередній Web Search Plugin.
Вони підтверджують навігацію та дедуплікацію, але не новий API-контракт.

Live-запуск `9d9fa8edfb1146b79ab2a2e4b17ff073` виконав три свіжі web searches
з лімітом 25 кожен. Провайдер повернув 20 + 20 + 20 citations, які об'єдналися
в 15 унікальних сайтів. За тестового `max_sites: 3` вибрано корені OLX, eStore
і Yandex Market; решта 12 доменів залишилися в `excluded_sites` з причиною ліміту.
Це також демонструє межу релевантності: навіть запит із OLX може повернути сторонні
сайти та інші країни. Дедуплікація доменів сама по собі не перевіряє ці умови.
Запуск зупинився на двох записах із Yandex; він доводить виконання discovery
й відкриття трьох коренів, але не завершення пошуку на кожному сайті.
Provider-reported cost свіжого запуску — $0.0492078395, із них web search $0.04624743.

Другий запуск `f28b9b34a159403a83a98e46e6129056` використав ту саму видачу з кешу
і `max_sites: 1`, щоб окремо перевірити весь шлях OLX:

```text
https://www.olx.ua/
  → спостережуваний input «Що шукаєте?» + submit
  → браузер вводить «MacBook Air 15 M4», очищує розпізнане поле локації
  → https://www.olx.ua/uk/list/q-MacBook-Air-15-M4/
  → два посилання на оголошення → JSON-LD + sparse enrichment
```

Пошуковий URL отриманий через справжню форму OLX, без зашитого шляху
та доданих параметрів фільтрації. Чотири завантажені стани, одна UI-взаємодія,
