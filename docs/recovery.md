# Захист від збоїв і продовження збору

Нові запуски зберігають стан під час роботи. Аварійне завершення Python, CLI
або API не повинно змушувати починати вже підтверджену роботу заново.
Продовження запускається явно: кнопкою **«Продовжити»** в історії або командою:

```powershell
uv run unified-parser resume RUN_ID --data-dir data
```

API: `POST /runs/{run_id}/resume` повертає `202` і продовжує той самий `run_id`.
Після перезапуску сервера спочатку можна переглянути збережені результати;
платні запити не поновлюються лише від відкриття історії.
Звіт попередньої спроби перед продовженням зберігається в `resume-history/`:
успішне відновлення не стирає інформацію про попередній збій.

## Що зберігається під час роботи

| Дані | Коли записуються | Де |
| --- | --- | --- |
| Валідний запис | До події `record` у live UI | `runs/RUN_ID/checkpoint.sqlite` і поточний DatasetStore |
| HTML | До extraction | `snapshots/` і журнал сторінок запуску |
| Черга, активна робота, завершені кандидати та плани | На межах виконання етапів | `checkpoint.sqlite` |
| Конфігурація, схема, стан discovery | Під час проходження відповідного етапу | `checkpoint.sqlite` та атомарні JSON-артефакти |
| Намір платного HTTP-запиту | До відправлення | `runs/RUN_ID/usage.jsonl` |
| Відповідь провайдера й отриманий usage | До семантичної перевірки та звичайного кешу | `usage-responses/` та `usage.jsonl` |

SQLite-транзакції та примусовий flush/fsync потрібні для підтвердження запису
перед наступною дією. Обов'язкові JSON-артефакти запуску та live snapshot
публікуються через тимчасовий файл і атомарну заміну. JSONL-відновлення допускає
лише обірваний останній запис: його залишок
зберігається окремо. Пошкодження всередині журналу не замовчується і не
перетворюється на порожній «успішний» запуск.

CSV/Parquet/JSONL експортуються окремо; вони не є єдиним місцем зберігання
незавершеного збору. Якщо процес загине до фінального експорту, записи
відновлюються з локальної бази саме цього запуску. Пізніший запуск того самого
профілю не підміняє ними історичний результат.

## Як працює продовження

1. Процес отримує блокування ОС для `run.lock`. Другий процес не може одночасно
   продовжити або перезаписати цей запуск. При аварійному завершенні ОС звільняє
   блокування; перевірка не спирається лише на PID чи час останньої активності.
2. Завантажуються збережені записи, схема, discovery і черга. Завершені
   сторінки та кандидати пропускаються. Для завантаженої, але не обробленої
   сторінки використовується збережений HTML.
3. Підтверджена відповідь AI відновлюється з обов'язкового сховища відповідей,
   навіть за `ai.cache: false`. Уже зафіксовані витрати враховуються один раз.
4. Решта роботи продовжується в межах загального бюджету запуску. Уже витрачені
   HTTP-спроби AI не обнуляються після перезапуску.

Якщо збір зупинився через заданий ліміт, для продовження його потрібно збільшити.
Ліміти рахуються для всього запуску, включно з уже виконаною роботою:

```powershell
uv run unified-parser resume RUN_ID --data-dir data --max-pages 1000 --max-records 5000
```

Можна змінювати ліміти, timeout/retries або явно вимкнути AI через `--no-ai`.
Зміна джерел, схеми чи провайдера потребує нового запуску: їх не підміняють
посеред відновлення. Фактично вибрані моделі фіксуються до першого AI-запиту;
зміна моделі в `.env` після збою не перемикає продовження на іншу модель.

Початкові schema/discovery, які встигли завершитися, не генеруються заново.
Якщо збій стався всередині такого етапу, збережені відповіді дозволяють завершити
його без повторної оплати підтверджених запитів.

Сесія браузера в пам'яті не переживає завершення процесу. Перед відновленням
очікуваної JS-дії система заново відкриває спостережену адресу й перевіряє
доступні елементи. Якщо стан змінився або дію неможливо однозначно прив'язати,
гілка завершується з неповним покриттям. Старий selector не натискається навмання.

## Витрати та невідомий результат запиту

Між відправленням запиту і надійним записом відповіді існує проміжок, у якому
провайдер уже міг списати кошти. Якщо процес загине саме там:

- намір запиту залишається в журналі;
- повна вартість позначається як невідома, відома сума зберігається;
- такий самий запит автоматично не надсилається повторно.

Звичайне відновлення не знімає цю невизначеність. Потрібна окрема перевірка
результату/рахунку провайдера перед свідомим новим запуском такої роботи.
Підтверджена відмова через брак кредитів відрізняється від невідомого результату:
явне продовження після поповнення дозволяє нову спробу, зберігаючи історію витрат.

При помилці обов'язкового запису на диск виконання зупиняється. Нові платні
запити не продовжуються на тлі втраченої можливості зберігати результати.
Журнал usage не містить ключів, заголовків авторизації чи запитів моделі;
окреме локальне сховище відповідей містить отримані дані й належить до даних запуску.

## Межі та перевірки

Захист розрахований на завершення процесу й перезапуск із працездатним сховищем.
Він не замінює резервну копію диска. Відмова самого сховища повідомляється явно.
Архівні запуски без нового checkpoint доступні для перегляду та `reprocess`,
але їхня втрачена черга чи usage не вигадуються заднім числом.

Автоматичні тести використовують тимчасові дані та mock/локальні провайдери:
аварійне завершення subprocess, відновлення записів і HTML, виключне блокування,
ідемпотентність, обірвані журнали, збої fsync/replace, неоплачуване повторне
читання відповідей та відмову від автоматичного повтору невідомих запитів.
Реальні платні пошуки для цих перевірок не потрібні.

```powershell
uv run pytest tests/integration/test_crash_recovery.py tests/integration/test_recovery_api.py -q
uv run pytest tests/unit/test_usage_journal.py -q
```

Механізми стандартної бібліотеки: [блокування Windows](https://docs.python.org/3.12/library/msvcrt.html#msvcrt.locking),
[fsync](https://docs.python.org/3.12/library/os.html#os.fsync),
[транзакції SQLite](https://docs.python.org/3.12/library/sqlite3.html#transaction-control).
