# Універсальне ядро та явно обрані профілі

Типовий `content_profile: generic` обробляє дані за схемою. Ціна, валюта,
виробник або характеристики пристрою не є обов'язковими ознаками запису.
Статті, вакансії, події, організації та інші сутності проходять той самий pipeline.
Це не гарантія розпізнавання будь-якої сторінки: зберігаються ліміти обходу,
контексту, можливості сайтів і обмеження доступу.

```text
Питання / URL + схема
  → пошук і навігація
  → JSON-LD / семантичний DOM / повторювані записи й таблиці
  → точні поля та явно задані mappings
  → LLM доповнює відсутні факти з вибраного evidence
  → валідація → збереження
```

## Межа між ядром і предметною логікою

| Налаштування | Типове значення | Призначення |
| --- | --- | --- |
| `content_profile` | `generic` | Універсальне виділення даних; `commerce` явно вмикає товарні евристики |
| `assessment_profile` | `generic` | Загальна оцінка; `device` явно вмикає перевірки пристроїв |
| `currency_aliases` | `{}` | Відповідності позначень валют лише для явно обраного commerce-профілю |
| `relevance_fields` | `null` | Необов'язковий перелік полів для правил релевантності |

Наявність полів `price` і `currency` у схемі не перемикає `generic` на `commerce`.
Організація чи стаття не повинна зникнути лише тому, що в ній згадується ціна.
У generic-режимі частини, аксесуари й послуги також не відкидаються як «не ноутбуки».

Стандартні відповідності на кшталт JSON-LD `headline` → `title` допомагають читати
семантичну розмітку. Власні поля зберігають свої значення; їхні назви не обмежені
словником товарів. Для ручної схеми підтримуються також Unicode-назви полів.

## Довільні поля та вкладені джерела

`x-source` у JSON Schema явно вказує, де брати значення з JSON-LD: dotted path
або локальний JSON Pointer. Це розширення extraction, а не інструкція моделі
вигадати поле чи виконати код.

```json
{
  "type": "object",
  "properties": {
    "author_name": {
      "type": ["string", "null"],
      "x-source": "/author/name"
    },
    "published_on": {
      "type": ["string", "null"],
      "x-source": "datePublished"
    }
  }
}
```

Для джерела `{"author":{"name":"Ada"},"datePublished":"2026-10-20"}` це дає
`{"author_name":"Ada","published_on":"2026-10-20"}`. Відсутній факт залишається
невідомим або передається на LLM extraction з вихідними даними як доказом.
Дати не отримують вигаданий часовий пояс, одиниці — довільну конвертацію.

Готовий приклад: [article.schema.json](../configs/schemas/article.schema.json)
і [articles-web.yaml](../configs/jobs/articles-web.yaml).

Коли сторінка містить `@graph` зі статтею, її видавцем і автором, можна явно задати
`"x-entity-types": ["Article", "NewsArticle", "BlogPosting"]` у схемі. Це відбирає
зазначені JSON-LD types без вгадування типу за назвами полів. Для інших завдань можна
вказати `Organization`, `Observation` чи власний точний тип, зокрема для сутностей
без назви. Стандартні `http(s)://schema.org/` type URI зіставляються з локальною назвою;
чужі namespaces не прирівнюються за випадковим однаковим закінченням.
Без цієї опції неоднозначні графи потребують AI-вибору або свідомого використання
rules mode, який проєктує відповідні структурні вузли, а не розуміє довільний намір.

```powershell
uv run unified-parser discover "Знайди події з астрономії. Збери назву, дату, місце, організатора та URL." --max-queries 1 --search-results 5
uv run unified-parser run configs/jobs/articles-web.yaml
```

У `discover` і `search --source` без `--config` схема створюється з питання.
Для `--no-ai` потрібна готова схема або `--fixed-schema`. Генератор має загальний контракт `title`
та `url` для ідентичності запису й довільні додаткові поля з питання. Він поки генерує
прості поля та масиви; складні вкладені структури задаються ручною JSON Schema.

## Коли потрібен товарний профіль

Профілі MacBook явно задають `content_profile: commerce` та
`assessment_profile: device`. Там доречні власна товарна пропозиція,
розділення діапазону цін і ціни конкретного товару, `offers` та MDM-перевірки.
Ці правила не застосовуються до всіх інших запусків за назвами полів.

```yaml
content_profile: commerce
assessment_profile: device
currency_aliases:
  грн: UAH
  ₴: UAH
```

Коди валют, явно задані джерелом, зберігаються без конвертації та обмеження
коротким списком USD/EUR/UAH. Символ `$` сам по собі не доводить USD: без
джерельного підтвердження чи явно заданої відповідності код залишається невідомим.
Зазначені в YAML відповідності належать конкретному завданню, а не універсальному ядру.

CLI також має `--content-profile generic|commerce` і
`--assessment-profile generic|device`. Зміна extraction-профілю не змінює автоматично
профіль оцінювання. JSONL/Parquet, історія та replay працюють для обох режимів.

## Перевірки на збережених реальних сторінках

HTML Python Documentation отримано зі справжнього HTTP-запиту до
`https://docs.python.org/3/library/asyncio.html`. Після виправлення розділення ARIA main,
меню й внутрішніх списків цей snapshot повторно оброблено в `generic` без AI та мережі.
Запуск `336df603439448889d6cd8ed89e3dd12` зберіг один запис із заголовком
`asyncio — Asynchronous I/O ¶`, оригінальним URL і текстом документації.
Цін чи валют у схемі немає; відсутні автор і дата залишені `null`.
Нуль errors/warnings, `ai: {}`. Початкові невдалі спроби збережені як історія,
а не як успішні приклади поточного коду.

Окремий replay двох раніше зібраних OLX-сторінок із явно обраним `commerce` дав
два записи з цінами 67 000 і 58 999 UAH. Запуск `c65d0bff13c5479f8f20ca3b1f4af4fb`
не виконував AI чи мережеві запити та не підтверджує поточну наявність оголошень.
